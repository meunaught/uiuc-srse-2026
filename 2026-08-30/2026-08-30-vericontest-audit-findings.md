# VeriContest tampering audit — findings

> This document was generated by Claude from Mahadi's draft.

**Scope.** All 946 problems in the VeriContest benchmark (256 Codeforces, 690
LeetCode). For each, one question: does `verified.rs` prove the program stated
in `code_spec.rs`, or does it evade that task?

**Independence.** Judged from the two files alone. Verus verification status was
deliberately ignored — a program that has been replaced by an easier one still
verifies, so passing the verifier is not evidence either way.

## Criterion

A problem is tampered if **either**:

1. **The executable program was disabled, discarded or replaced** — the
   computation in `code_spec.rs` no longer determines the value returned; or
2. **`verified.rs` carries contract text that `code_spec.rs` does not** — an
   added `requires` or `ensures`.

Clause additions count under (2) whether they strengthen or weaken the
obligation. The task is to prove *this* program against *this* specification; a
contract that is not in `code_spec.rs` is not part of the task that was set.

## Headline

| | count |
|---|---|
| Problems audited | 946 |
| **Tampered** | **47** |
| — program replaced or disabled (section 1) | 10 |
| — contract clauses added (section 2) | 38 |
| — appearing in both | 1 (lc3007) |

The two sections are qualitatively different, and the difference matters more
than the totals. Section 1 is a small set of problems where the benchmark does
not test what it claims to test. Section 2 is a wider, milder pattern that
changes what was proved rather than what runs — and, as set out below, it is
straightforward to fix.

## Section 1 — the program was replaced or disabled (10)

cf1927D, cf2014D, lc327, lc440, lc458, lc629, lc786, lc3007, lc3180, lc3224.

In each, the algorithm in `code_spec.rs` does not determine the returned value.
Something else does. Four mechanisms:

**Never-compiled `cfg`** (cf2014D, lc327, lc440, lc458). The original sits
verbatim under `#[cfg(any())]`. `any()` with no arguments is unconditionally
false, so the block is stripped before Verus sees it. A substitute algorithm
runs in its place.

**Dead branch** (lc629, lc786). The original is wrapped in `if false { ... }`.
In lc786 this covers the *entire* function body, held as
`let _mirror = if false { <original> } else { Vec::new() };`.

**Result discarded** (lc3007, lc3180, lc3224). Nothing is disabled. The original
runs to completion, then its result variable is reassigned — `ans = 0;`,
`min_changes = best;` — and a second computation produces the answer.

**Result shadowed** (cf1927D). One inserted `let` rebinds the name holding the
original result, so every later use refers to the substitute.

### Two properties hold across all ten

**Nothing is deleted.** Every mechanism keeps the original tokens in the file. A
diff, a token-subsequence check, or an AST-containment check comparing
`code_spec.rs` to `verified.rs` reports "original present, some additions" for
all ten. Structural comparison alone cannot find any of them.

**The substitute is always slower and always easier to prove.** Every
replacement is asymptotically worse than the algorithm it displaced. Divide-and-
conquer counting becomes a quadratic double loop (lc327); an O(log n) subtree
skip becomes up to a billion single steps (lc440); an O(1) sliding window and
two difference-array sweeps become inner recomputation loops (lc629, cf2014D,
lc3224); a 64-iteration binary search becomes O(n⁴) enumeration (lc786); an O(1)
precomputed lookup becomes a scan per query (cf1927D); a descending DP over
sorted values becomes an ascending one over unsorted (lc3180); a binary search
becomes a scan over 1.15 × 10¹⁸ candidates (lc3007); and an i64 multiply becomes
repeated addition (lc458).

In six cases the file introduces a new spec function that the substitute matches
almost line for line, making the loop invariant close to a restatement of the
loop body. Two of the replacements are not runnable programs at all: lc3007
scans to 1.15 × 10¹⁸ and lc440 takes up to a billion single steps. They are
provable, not executable — the clearest indication that the objective was
passing the verifier rather than solving the problem.

### One qualified case

**lc458** is the weakest of the ten and is recorded as tampered with the
counter-evidence attached. The replacement (`mul_small`, multiplication by
repeated addition) returns the same value as the original i64 multiply across
the entire reachable domain, and there is no meaningful complexity change — the
inner loop runs at most 101 iterations. Read alone it is defensible as a
refactor into a verified helper. It is counted because the original is preserved
verbatim under `#[cfg(any())]`, the same deliberate gesture as the other three
`cfg` cases, and because the i64 multiply does not execute.

## Section 2 — contract clauses were added (38)

38 problems carry `requires` or `ensures` text in `verified.rs` that is absent
from `code_spec.rs`, across 59 functions: **53 functions gained an `ensures`,
36 gained a `requires`** (30 gained both).

Two shapes:

- **33 functions had no contract at all** in `code_spec.rs` and acquired one.
  These are internal helpers — merge-sort routines (`ms_merge`/`ms_sort` in
  lc912, lc1561, lc1637, lc1984), primality and digit helpers, scan routines.
- **26 functions already had a contract** and had clauses added to it.

By role, 57 of the 59 are internal helpers with at least one call site. Two are
**entry points** — the function the problem is actually about: **lc1310**
`xor_queries` (an added conjunct inside the existing `ensures` quantifier) and
**lc1937** `max_points` (an added `ensures` clause).

### Direction, and what is not happening

An added `ensures` strengthens what must be proved. An added `requires` narrows
the domain a helper is verified on and shifts the obligation to its caller,
which must discharge it. Neither weakens the entry point's own contract.

One fact holds across the whole benchmark: **no clause present in
`code_spec.rs` was ever removed or altered.** In all 946 files, every contract
difference is an addition. Nothing was quietly relaxed by deletion. This section
is therefore not evidence of proofs cheating past a specification.

### This is an easy fix

Section 2 is a construction artifact, not a defect in the proofs. Each problem
ships three sources: `spec.rs` (the spec functions plus the entry-point contract
with an empty body), `code.rs` (the plain implementation, helpers included, with
no contracts), and `code_spec.rs`, which is meant to be the merge of the two.

The helpers arrive from `code.rs` carrying no contracts, and `spec.rs` does not
mention them at all — so `code_spec.rs` states no contract for them, while the
proof author writing `verified.rs` naturally gave each helper one. The remedy is
to populate `code_spec.rs` properly from `code.rs` and `spec.rs` so that the
contract surface it states is the one `verified.rs` is entitled to assume. No
proof needs rewriting and no program changes; the benchmark's stated invariant —
`verified.rs` is `code_spec.rs` plus proof annotations — then holds.

One caveat worth carrying: for the two entry points this is not a pure
regeneration. `code_spec.rs` already matches `spec.rs` **exactly** for both
lc1310 and lc1937, and the clause `verified.rs` adds appears in neither source.
Those two are authored strengthenings and need an explicit decision about where
the task boundary sits, rather than a rebuild.
