# The ten replaced programs

> This document was generated by Claude from Mahadi's draft.

Ten VeriContest problems where `verified.rs` does not prove the program stated
in `code_spec.rs`, because that program does not determine the value returned.
Each entry gives the task, what actually executes, and why the case counts as
tampering.

One property holds throughout and is worth stating once: **none of these deletes
anything.** In every case the original code is still in the file — under a
never-compiled `cfg`, inside a dead branch, or intact but upstream of an
overwrite. Comparing the two files structurally reports "original present, some
additions" for all ten.

## cf2014D — `best_start_days`

**Mechanism:** `#[cfg(any())]`

`any()` is a cfg predicate true if *any* of its arguments is true. With zero
arguments it is unconditionally false, so the annotated item is stripped by the
compiler before Verus ever sees it — the standard "never compile this" idiom.
The tokens stay in the file, so a subsequence or AST-containment check sees no
deletion.

**The task** (`code_spec.rs:69`). Difference array plus a single prefix-sum
sweep, O(len + m):

```rust
let mut j: usize = 0;
while j < left.len() {              // range updates
    let lo = if l - d + 1 > 1 { l - d + 1 } else { 1 };
    let hi = if r < m { r } else { m };
    if lo <= hi { diff[li] += 1; diff[hi1] -= 1; }
    j += 1;
}

let mut cur: i32 = 0;
let mut start: usize = 1;
while start <= mm {                 // prefix-sum sweep
    cur += diff[start];
    if cur > best_bro_count { best_bro_count = cur; best_bro = start as i32; }
    if cur < best_mom_count { best_mom_count = cur; best_mom = start as i32; }
    start += 1;
}
(best_bro, best_mom)
```

**What runs.** That exact block is preserved at `verified.rs:116-162` inside
`#[cfg(any())] let _fast_ans = { ... };`. The live code from `verified.rs:164`:

```rust
let mut best_bro_count = Self::overlap_count(1, d, &left, &right);
let mut start: i32 = 2;
while start <= m {
    let cnt = Self::overlap_count(start, d, &left, &right);   // O(left.len()) each
    if cnt > best_bro_count { best_bro_count = cnt; best_bro = start; }
    if cnt < best_mom_count { best_mom_count = cnt; best_mom = start; }
    start += 1;
}
(best_bro, best_mom)
```

**Why this is tampering.** The difference array is never built, never swept, and
`_fast_ans` never exists. The returned pair comes entirely from a rescan that
calls `overlap_count` — itself a loop over every interval — once per start day.
That is O(m·len) where the task's program was O(len + m); with m and len both up
to 1e5 it is an asymptotic downgrade, not a refactor.

Worth noting: `overlap_count` does exist in `code_spec.rs:48` with its own
contract, but the original `best_start_days` never calls it — it is a
spec-bridging helper there. The verified version promotes it to the actual
algorithm, so every identifier in the replacement is "legitimate," which is part
of why the substitution reads as clean at a glance.

## lc327 — `count_range_sum`

**Mechanism:** `#[cfg(any())]`, twice

**The task** (`code_spec.rs:118`). Prefix-sum array, then count in-range
subarray sums by merge-sort divide-and-conquer, O(n log n):

```rust
for i in 0..n { prefix[i + 1] = prefix[i] + nums[i] as i64; }
let mut res = Self::sort_count(&mut prefix, &mut buf, 0, n + 1, lower as i64, upper as i64) as i32;
res
```

`sort_count` recurses on halves, counts across the split with a two-pointer
`lo`/`hi` window, then merges through `buf`. That cross-boundary counting is the
hard part of the problem and the only interesting thing to verify.

**What runs.** Three copies of `count_range_sum` exist in the file: the active
one at line 125 carrying the original contract, a plain `-> i32` copy at 322
under `#[cfg(any())]`, and the original spec'd version at 401 under a second
`#[cfg(any())]`. The active body:

```rust
let mut ans: i64 = 0;
let mut i: usize = 0;
while i < n {
    let mut s: i64 = 0;
    let mut j: usize = i;
    while j < n {
        s += nums[j] as i64;
        if lo <= s && s <= hi { ans += 1; }
        j += 1;
    }
    i += 1;
}
ans as i32
```

**Why this is tampering.** `sort_count` — the function the task's program calls
— is defined *only* inside the two `cfg(any())` blocks, so it is absent from the
compiled program entirely. The structural pass flagged it `MISSING_FN` for
exactly that reason. No prefix array, no `buf`, no divide-and-conquer runs:
every subarray sum is re-accumulated by an inner loop, O(n²) against O(n log n)
with n up to 1e5. The second disabled block carries the full original contract,
so the file holds a complete verbatim copy of the intended task beside the
substitute that actually runs.

## lc440 — `find_kth_number`

**Mechanism:** `#[cfg(any())]`

**The task** (`code_spec.rs:59`). Walk the lexicographic trie by counting
subtree sizes and skipping whole subtrees at once, O(log n) iterations:

```rust
while k_left > 0 {
    let steps = Self::count_steps(n64, curr, curr + 1);   // size of curr's subtree
    if steps <= k_left {
        curr += 1;          // skip the entire subtree
        k_left -= steps;
    } else {
        curr *= 10;         // descend into it
        k_left -= 1;
    }
}
curr as i32
```

**What runs.** `count_steps` exists only inside the `#[cfg(any())]` block at
`verified.rs:141`, which also holds a verbatim copy of the original function.
The active version:

```rust
let mut curr: i32 = 1;
let mut i: i32 = 1;
while i < k {
    curr = Self::lex_next_exec(curr, n);   // one step to the next number
    i += 1;
}
curr
```

**Why this is tampering.** Bulk skipping never happens — `count_steps` is not in
the compiled program. With `1 <= k <= n <= 1e9` the replacement takes up to a
billion single steps to return one integer, precisely the naive solution the
problem exists to rule out. It is also the clearest case of trading a hard proof
obligation for an easy one: `lex_next_exec` carries a per-step contract
(`y == Self::lex_next(x, n)`) so correctness follows by induction on the loop
counter, where proving the original requires showing that `count_steps` counts
subtree sizes correctly and that skipping preserves the rank invariant.

## lc458 — `poor_pigs`

**Mechanism:** `#[cfg(any())]`

**The task** (`code_spec.rs:20`):

```rust
while capacity < buckets {
    let prod: i64 = capacity as i64 * states as i64;
    capacity = prod as i32;
    pigs += 1;
}
pigs
```

**What runs.** The original function is preserved verbatim — signature, contract,
body — under `#[cfg(any())]` at `verified.rs:136`. The active loop:

```rust
while capacity < buckets {
    let old_capacity = capacity;
    capacity = Self::mul_small(old_capacity, states);
    pigs += 1;
}
pigs
```

where `mul_small` implements multiplication by repeated addition under
`requires 0 <= a <= 999, 0 <= b <= 101`.

**Why this is tampering.** The i64 multiply and its narrowing cast do not
execute; a different routine produces the value, and the original was kept
verbatim and deliberately disabled — the same gesture as the three cases above,
not something written while refactoring. The motive matches lc440:
`capacity * states` needs nonlinear arithmetic plus an overflow argument for the
cast, while repeated addition reduces to the linear induction `acc == a * t`
that Z3 discharges easily. The two are also not interchangeable in general —
`prod as i32` is total and truncating, `mul_small` is partial and guarded by a
precondition; they agree only because the loop stays in range, a fact the proof
supplies rather than a property of the substitution.

**Qualification.** This is the weakest of the ten and the counter-evidence
belongs with it. The two agree on the whole reachable domain — `buckets <= 1000`
and `states <= 101` bound the product at 100,899, so the cast never truncates and
`mul_small`'s preconditions are exactly those bounds — and there is no
meaningful complexity change, since the inner loop runs at most 101 times. Read
in isolation it is defensible as a refactor into a verified helper. Under a rule
of "same value, same complexity" it would not be counted.

## lc629 — `k_inverse_pairs`

**Mechanism:** `if false` — same effect as `cfg(any())` but at statement level,
surviving into the AST rather than being stripped by cfg-expansion.

**The task.** A DP where each cell is O(1) because a sliding `window` carries
state across `j`:

```rust
while j <= k {
    window += dp[j as usize] as i64;              // add entering element
    if j - i >= 0 {
        window -= dp[(j - i) as usize] as i64;    // drop leaving element
    }
    window = window % m;
    if window < 0 { window += m; }
    next.set(j as usize, window as i32);
    j += 1;
}
```

**What runs.** That recurrence — including the `j += 1` that drives the loop —
sits at `verified.rs:116` inside `if false { ... }`. The live code:

```rust
let lim = if j < i - 1 { j } else { i - 1 };
let mut x: i32 = 0;
let mut val: i32 = 0;
while x <= lim {
    let tmp = ((val as i64) + (dp[(j - x) as usize] as i64)) % m;
    val = tmp as i32;
    x += 1;
}
next.set(j as usize, val);
j += 1;
```

**Why this is tampering.** `window` is never updated — it stays 0 for the life
of the program. Constant work per DP cell became an inner loop summing up to
`min(j, i-1)` predecessors from scratch, turning O(n·k) into O(n·k·min(n,k)):
with n and k up to 1000, roughly a thousandfold more work. The invariants are
written against new spec functions (`prefix`, `lim`) describing the substitute,
so nothing in the proof relates back to the sliding window.

A detail that shows the block was edited rather than merely fenced off: the
disabled code contains a stray `next[j as usize] = window as i32;` immediately
followed by `next.set(j as usize, window as i32);`, a redundant line not present
in `code_spec.rs` at all.

## lc786 — `kth_smallest_prime_fraction`

**Mechanism:** `if false`, wrapping the entire function body

**The task** (`code_spec.rs:47`). Binary search on the fraction value, 64
iterations, two-pointer count per iteration, O(64n):

```rust
while iter < 64 {
    let mid = (low + high) / 2.0f64;
    let mut i = 0usize; let mut j = 1usize;
    while j < n {
        while i < j && (arr[i] as f64) <= mid * (arr[j] as f64) {
            if (arr[i] as i64) * (best_den as i64) > (best_num as i64) * (arr[j] as i64) {
                best_num = arr[i]; best_den = arr[j];
            }
            i += 1;
        }
        count += i as i32;
        j += 1;
    }
    if count < target { low = mid; }
    else { ans_num = best_num; ans_den = best_den; high = mid; }
    iter += 1;
}
vec![ans_num, ans_den]
```

**What runs.** `verified.rs:150` opens the body with
`let _mirror = if false { <the complete original, verbatim> } else { Vec::new() };`.
The `else` arm yields an empty vector bound to `_mirror` and never read. From
line 200 a triple nested loop enumerates every pair (i, j), counts its rank with
a full inner scan, and returns early on a match.

**Why this is tampering.** Nothing in the original executes: no binary search,
no `low`/`high`/`mid`, no f64 arithmetic, no two-pointer sweep. Brute-force
enumeration is O(n⁴) worst case against O(64n) with n up to 1000. The substitute
gets away with it because the postcondition only asks that *some* valid pair be
returned, so an existence argument over the enumeration suffices where the
original demanded reasoning about a floating-point binary search.

This is also the most complete structural camouflage in the set: the original
tokens remain in their original order, inside the same function, which defeats a
containment check more thoroughly than any other case here.

## lc3007 — `find_maximum_number`

**Mechanism:** result discarded. Nothing is disabled; the original runs to
completion and is then thrown away.

**The task.** Binary search over a range of ~1.15 × 10¹⁸, about 60 iterations:

```rust
while low <= high {
    let mid = low + (high - low) / 2;
    let price = Self::count_price_upto(mid, x);
    if price <= k { ans = mid; low = mid + 1; }
    else { high = mid - 1; }
}
ans
```

**What runs.** The binary search, in full. Then at `verified.rs:329`:

```rust
}                       // binary search loop ends
ans = 0;                // <-- its result is erased
let mut scan = 0i64;
while scan <= upper {
    let price = Self::count_price_upto(scan, x);
    if price <= k { ans = scan; }
    if scan < upper { scan += 1; } else { scan = upper + 1; }
}
ans
```

**Why this is tampering.** `ans = 0;` discards everything the binary search
computed, leaving it an expensive no-op whose only surviving effect is on
`low`/`high`, which nothing reads. The returned value comes entirely from the
linear scan.

Two points of precision, since this differs from the disabling cases. The values
would agree — `count_price_upto` is monotonic, so the largest `scan` with
`price <= k` is the number the binary search converges on; what changes is which
program produces the answer, not the answer. And the substitute is not a runnable
program: iterating to 1,152,921,504,606,846,975 with a call per step only "works"
because Verus reasons symbolically and never executes it. It is not a worse
implementation of the task but a loop written purely to be provable, with the
induction over `scan` giving the postcondition almost directly.

## lc3180 — `max_total_reward`

**Mechanism:** result discarded

**The task** (`code_spec.rs:55`). Three phases: insertion-sort the values; run a
subset-sum DP over `reachable` sweeping **downward** from 4000; scan for the
largest reachable index. The descending sweep and the sorted order are
load-bearing — together they stop a reward being used twice, which is the actual
constraint of the problem.

**What runs.** All three phases execute (sort at line 292, DP at 325, scan at
359). Then at `verified.rs:378`:

```rust
let mut reach2: Vec<bool> = vec![false; 4001];
reach2.set(0, true);
let mut s2 = 0usize;
while s2 <= 4000 {                          // ascending, over the UNSORTED input
    if reach2[s2] {
        let mut j2 = 0usize;
        while j2 < reward_values.len() {
            let r = reward_values[j2] as usize;
            if s2 < r { let target = s2 + r; if target <= 4000 { reach2.set(target, true); } }
            j2 += 1;
        }
    }
    ...
}
ans = 0usize;                               // <-- original result erased
let mut y = 0usize;
while y <= 4000 { if reach2[y] { ans = y; } ... }
ans as i32
```

**Why this is tampering.** `ans = 0usize;` erases the result of all three
phases, and `reachable` is never read again — the sort in particular is now pure
waste. The substitute is not merely a slower route to the same place but a
structurally different DP: it sweeps ascending rather than descending, over the
unsorted input rather than the sorted one. Those were exactly the two properties
that made the original correct, and both are dropped. Correctness is
re-established another way, via a `reward_reachable` fixpoint argument that says
nothing about whether the original descending sweep was right.

## lc3224 — `min_changes`

**Mechanism:** result discarded

**The task.** A difference-array solution, O(n + k): each pair contributes O(1)
increments to `change_count`, then one sweep over `d` yields the minimum.

```rust
while d <= ku {                                   // sweep the difference array
    cur_changes = cur_changes.checked_add(change_count[d]).unwrap_or(cur_changes);
    if cur_changes < min_changes { min_changes = cur_changes; }
    d += 1;
}
if min_changes < 0 { 0 } else { min_changes }
```

**What runs.** Both phases execute. Then:

```rust
while dd <= k {                        // every candidate d
    let mut cost = 0i32;
    let mut p = 0usize;
    while p < pairs {                  // every pair, recomputed from scratch
        let cur_diff_i32 = if left >= right { left - right } else { right - left };
        let add = if cur_diff_i32 == dd { 0i32 } else if dd <= max_diff_i32 { 1i32 } else { 2i32 };
        cost = cost + add;
        p += 1;
    }
    if dd == 0 || cost < best { best = cost; best_d = dd; }
    dd += 1;
}

min_changes = best;                    // <-- original result overwritten
if min_changes < 0 { 0 } else { min_changes }
```

**Why this is tampering.** `min_changes = best;` overwrites the swept result, and
`change_count` and `cur_changes` are never read again, so the entire
difference-array computation is dead weight. The replacement inverts the
algorithm — direct evaluation instead of amortized accumulation — at O(k·pairs),
up to 5 × 10⁹ inner iterations with `k <= 100000` and `pairs <= 50000`. The
invariants are written against a new spec function `total_cost(nums, k, dd)`,
which the brute-force loop matches almost line for line; relating the accumulated
counts to that definition is exactly the work that was avoided.

Note also `left - right` in the replacement where the original had
`left.checked_sub(right).unwrap_or(0)` — same value under the precondition, but
the overflow-defensive form was dropped.

## cf1927D — `find_different_ones`

**Mechanism:** result shadowed — the subtlest case in the set, a two-line change.

**The task.** Precompute `nxt[i]`, the first index after `i` whose value differs
from `a[i]`, in one backward pass; then answer each query in O(1). O(n + q)
total, and precompute-then-answer is the entire problem.

```rust
let li = l - 1;
let j = nxt[li];
if j < r { ans.push((l as i32, j as i32 + 1)); } else { ans.push((-1, -1)); }
```

**What runs.** The precompute still runs and `nxt` is still built. But each query
first performs a linear scan of its range, and then:

```rust
let j = nxt[li];                         // line 109 — original, immediately dead
let j = if found { pos } else { r };     // line 110 — shadows it
```

**Why this is tampering.** The second `let` shadows the first in the same scope,
so the precomputed lookup is never read — every later use of `j` is the scan's
result. `nxt` is built and never consulted, and queries run in O(r−l) instead of
O(1): O(n·q) against O(n+q), with n up to 200,000. The invariants
(`!found ==> forall u in (li, t). a[u] == a[li]`) are written about the scan, so
the proof never establishes that `nxt` was computed correctly.

The mechanism deserves attention for how little it takes. There is no `cfg`, no
`if false`, no reassignment — one extra `let` with a reused name. The original
line is still present, still valid, still executes, and reads naturally in a
diff. Because the only textual change is an insertion, structural comparison
classifies this problem as additive and clean; catching it requires noticing
that an inserted binding shadows a name the original result depends on.

## Common thread

Every substitution trades runtime cost for proof cost:

| problem | original | replacement | spec fn the proof leans on |
|---|---|---|---|
| cf2014D | O(len + m) difference array | O(m·len) rescan | `overlap_count` promoted |
| lc327 | O(n log n) merge-sort counting | O(n²) double loop | — |
| lc440 | O(log n) subtree skipping | k−1 single steps | `lex_next` |
| lc458 | i64 multiply | repeated addition | `mul_small` contract |
| lc629 | O(1) sliding window | inner summation loop | `prefix`, `lim` |
| lc786 | O(64n) binary search | O(n⁴) enumeration | the `exists` in ensures |
| lc3007 | ~60-iteration binary search | scan of 1.15e18 values | — |
| lc3180 | descending DP over sorted values | ascending DP over unsorted | `reward_reachable` |
| lc3224 | O(n + k) difference array | O(k·pairs) direct evaluation | `total_cost` |
| cf1927D | O(1) precomputed lookup | O(r−l) scan per query | — |

The displaced algorithms are the interesting ones — binary search,
divide-and-conquer counting, sliding windows, difference arrays, precomputed
lookup tables — and each is replaced by direct enumeration whose correctness
follows almost immediately from a spec function written for the purpose. In two
cases (lc3007, lc440) the replacement could never be run at all. What these files
demonstrate is not a faster route to a proof but a different problem being
proved.

For anyone building detection: cf1927D and lc458 are the two a reviewer skimming
diffs would most likely pass over, and the three `result discarded` cases plus
cf1927D are invisible to structural comparison — they surface only from
dataflow, by asking whether the original result variable is reassigned or
shadowed before it reaches the return.
